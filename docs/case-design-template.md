# 测试用例设计文档模板（仅需求）

> 用途：新 Client/新模式/结构变更的设计文档产出依据。仅列「必须覆盖什么」与「形态」，不填示例、不画架构图、不给接口签名样例、不列素材清单表。可选节可填 N/A。
> 何时需要：出现新 Client / 新模式 / 结构变更时必写；纯单接口用例补充可省。
> 场景/分层归属、复用、代码自查 → `test-case-development-flow.md` 决策 0 / 步骤 3 / 步骤 5；框架/业务边界 → 该流程决策 5 一句话。

## 1. 背景、约束与目标（REQUIREMENTS）
- 业务背景：动因（来自需求/缺陷/回归的 why，非步骤）
- 设计约束：对全部用例/代码路径生效——分层归属、资源语义、后端隐式约束（含错误码）
- 通用预检清单：环境/资源状态；skip 与 fail 的判据
- 用例清单：每场景一行（ID + 方法 + 一句话 + phase；ID 形如 `API-<Domain>-<Action>`）
- 每场景约束表：形态 `场景｜约束｜说明`，目标执行代码零 if/else（所有分支转为属性/前置条件）

## 2. 设计逻辑（REQUIREMENTS）
- 每个权衡记为一行：`挑战→取舍选择→放弃理由`（无权衡则给结论）
- 长/可重复流程：分阶段；状态检查点（持久化/续跑粒度）；幂等

## 3. 核心数据结构（REQUIREMENTS）
- Model 字段对齐后端 JSON tag
- 复杂体用 `Builder`（链式 `with_*` + `build`）
- 便捷属性（如 `organization_name = metadata.name`）须注明来源

## 4. 接口定义（REQUIREMENTS）
- 每行形态：`签名 + 一行职责 + 协作摘要（与 X 通信：A→B→C）`；签名只写 `def name(...)` 形态，不展开实现
- 复用存量 Client，不新建副本（grep 根 `conftest.py` + 注册表已确认）

## 5. 一致性校验（REQUIREMENTS）
- 1 的每用例有对应 `test_` 方法
- 2 的每个操作在 4 有对应接口
- 文档↔实现 diff 表（实现/运行时填）

## 6. 变更历史（REQUIREMENTS）
- 每变更一行：`版本｜日期｜变更｜原因`
- 基线=设计起点（分支/提交/代码文件记于 1），非被放弃的中间设计

> 成型后对照第 5 节做一致性自检，再进入 `test-case-development-flow.md` 步骤 4。
