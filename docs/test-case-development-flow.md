# 测试用例开发流程（防返工）

> 核心原则：**先决策，后写码**。绝大多数返工（评审重构、等环境、文档返工）都是把本该在写码前做的决策推迟到了写码之后。
> 适用范围：新 Client / 新模式 / 结构变更 / 重资源长流程必走；纯单接口小用例可只做决策 0 的 1–4 项。

## 决策 0：六项前置决策（写码前定）
| # | 决策 | 要点 |
|---|------|------|
| 1 | 校验点 | 操作→断言→通过标准；断言不夸大（一切决策的前提）；指导书中"遇到报错怎么做"要转成**提前检查项/提前规避项** |
| 2 | 场景归属 | REST 接口→API 用例目录；节点/集群命令→SSH 用例目录 |
| 3 | 分层 | client=`HTTPClient` / ssh=`SSHExecutor` / utils=纯工具 / orchestration=`Pipeline`；SSH 操作禁止进 client 层 |
| 4 | 复用核查 | 先 grep 根 `conftest.py` + fixtures/clients 注册表（`examples/conftest.py` 为范例）；同职责→复用或扩展 Client，不重复造 |
| 5 | 模块边界 | 单职责文件清单；圈复杂度<6；复杂用例另定架构（见下「复杂用例架构三要件」）；**框架/业务边界一句话**：具体概念/数据格式→业务工程；通用机制或被>3 个域复用→框架（testkit）；单场景专用→业务 |
| 6 | 设计文档 | 新 Client/新模式/结构变更→写码前先读 `docs` 设计文档，而非写后补；设计文档产出要求见 `case-design-template.md` |

**产出**：一页纸 = 校验点 + 分层归属 + 文件清单（每文件一行职责）+ 依赖的存量资产。此页即步骤 4 评审的契约。
**评审检查单**：6 项齐全 + 文件清单职责不重叠 + 复用点已列，否则退回决策 0。

## 复杂用例架构三要件（决策 5 展开）
1. 依赖方向单向：被依赖方不反向 import 依赖方（无环）
2. 状态机/续跑：检查点字段 + 持久化位置 + 续跑粒度三者明确
3. 幂等：同输入重跑结果一致，可安全跳过已完成步

## 输入清单（步骤 1 的原始素材）
1. **操作指南文档**：需转为 Markdown；图片内容手动补充（如截图里成功的返回字符是什么）
2. **测试用例**：原始用例描述
3. **API 文档**：接口定义来源

> 三条素材都要带来源标注地转入 `docs/<feature>/`；命令/截图转写为文本时，明确标注出自哪份原始文档。

## 用例流程图记号（步骤 1 转写 + 步骤 2 拆分依据）
每个不确定、顺序不同的操作都要画流程图并标注决策点：
1. 用 `===` 双等号线分割大阶段，格式：`=== 阶段标题 ===`
2. 同阶段内用树状连接符：`├──`（非结尾）、`└──`（结尾）、`│`（延续）
3. 方法调用用 `->` 表示调用链，方法名后括号标注关键参数
4. 跳过条件用 `[skip]` 前缀标注，分支逻辑用 `[条件名]` 标注
5. 嵌套方法展开为多级缩进，展示实际调用关系
6. 每个用例先输出一行标题：`用例编号 - 用例名称`
7. 画完后**用流程图核对执行逻辑/编排顺序是否与预期一致**，不一致先回到决策 0

## 公共函数决策门
- 能抽取公共函数的操作 → 抽为公共函数 / Client 方法复用
- **不能抽取公共函数的操作 → 必须提出决策并记录**（为何不能复用、是否需新增抽象），纳入决策 0 一页纸

## 五步流程（每步以前步为 gate）
1. 原始文档→Markdown（存 `docs/<feature>/`，<501 行；截图/命令输出转写为带来源标注的文本；每条命令标注来源文档）—— **命令来源纪律**：执行命令优先从业务代码库分析获取，先写成单步测试小脚本在环境中实跑、完整取得返回信息，确认现状后再写入用例 — gate：原文无遗漏、来源可追溯、命令已单步验证
2. 拆分场景 + 前置约束（变体维度交叉→一个 `test_` 方法一个场景；所有「若 X」转为场景属性或前置条件；**目标：执行代码零 if/else**；拆分依据为上方流程图记号）— gate：每个 if/else 已下沉为场景属性
3. 清点资产，不重建（fixtures：grep 根 `conftest.py`；client：缺能力加方法而非 fixture patch；config：fixture 动态→YAML>`env`；复用资产见 testkit 各层能力（`index.md` 特性表 / `user-guide/`），新能力优先在对应层加方法；红线：不重复 client/fixture）—— **配置前期准备**：梳理需要的配置/信息（超时参数、文件命名、目录、系统架构、k8s 查询导出等），前期一次性准备好；除变量外，运行时不额外获取信息（如运行中去读文件、跑命令取一次性信息、外部接口申请资源） — gate：无重复资产、复用点已列、配置已前置
4. 写计划文档 + 代码骨架（按执行顺序分 phase→`docs/<feature>-plan/`；骨架：核心类、`test_` 文件、配置模型、`conftest.py`）— gate：决策 0 一页纸被评审通过
5. 分阶段实现 + 自查（见下）— gate：每段代码过自查 5 项

## 每段代码自查 5 项
1. 三段式 docstring（前置/测试/预期）+ 带 `msg` 的断言；断言只验证本步骤承诺，不顺便校验后端无关字段（不夸大）
2. 分层合规：`Client` 返回 `Model`（非裸 dict），`Model` 不持有 `Client` 引用；复杂体用 `Builder`，请求头走 `extra_headers`，不硬编码密码；用 logger 不用 print
3. 异常不吞（空 `except` 必有注释）；`yield` 清理放 `try/finally`；`__init__.py`/`conftest.py` 不写业务
4. 圈复杂度<6，无可变默认参；等待用 `WaitHelper` 轮询，不用固定 `sleep`；长等可用 `testkit_wait_helper` 夹具
5. `python -m py_compile` + `pytest --collect-only` 通过

## 长流程/重资源操作铁律
- 幂等 + 断点续跑（每步后写状态标记，执行前检查，跳过已完成；重跑从断点续，绝不重建环境）→ 编排层用 `Pipeline`（`--testkit-resume-from`）
- 即时清理注册（操作后立刻 `testkit_cleanup.register(...)`，非用例末尾）；失败保留现场用 `--testkit-skip-cleanup-on-failure`
- 两级验证（先轻量逻辑验证（mock/无副作用读）→收敛→一次真实资源端到端；续跑作兜底）
- **用例隔离纪律**：每个用例可独立运行；功能交叉的用例在某用例失败后，保留故障现场、**不执行**功能交叉的其余用例（避免现场被覆盖、定位困难）

## 收尾
失败从 `logs/` 定位 → 修 bug 后 grep 同模式出现处（同方法/同模式/同资源依赖）→ 按同步规则更新受影响 `docs/` 文档。

## 返工来源对照
| 返工症状 | 根因 | 前置动作 |
|----------|------|----------|
| 评审要求重构分层 | 决策 3 缺失 | 写码前定分层归属 |
| 等环境/配置缺失 | 决策 4 漏查 / 配置未前置 | 先 grep 资产 + 配置前期准备 |
| 文档返工 | 决策 6 倒置 | 写码前读设计文档 |
| 重复 client/fixture | 复用红线失守 | 同职责复用/扩展 |
| 重跑重建环境 | 无幂等续跑 | 编排层内置续跑 |
| 现场被交叉用例覆盖 | 缺用例隔离纪律 | 失败即停、不跑交叉用例 |
| 命令与文档不符 | 命令未单步验证 | 业务库分析 + 单步脚本确认 |

> 一句话：写码前 30 分钟定 6 项、实现中自查 5 条、编排层内置幂等续跑、每轮仅一次真实资源验证——评审级返工基本消除。
